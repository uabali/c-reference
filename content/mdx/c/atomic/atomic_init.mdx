<p class="decl-header">Defined in header <code>&lt;stdatomic.h&gt;</code></p>

```c
void atomic_init( volatile A* obj, C desired );
```

<p class="decl-note"><span class="std std-since std-c11">(since C11)</span></p>

<p>Initializes the default-constructed atomic object <code>obj</code> with the value <code>desired</code>. The function is not atomic: concurrent access from another thread, even through an atomic operation, is a data race.</p>

<p>This is a <a href="/reference/c/language/generic/">generic function</a> defined for all <a href="/reference/c/language/atomic/">atomic object types</a> <code>A</code>. The argument is pointer to a volatile atomic type to accept addresses of both non-volatile and <a href="/reference/c/language/volatile/">volatile</a> (e.g. memory-mapped I/O) atomic objects, and volatile semantic is preserved when applying this operation to volatile atomic objects. <code>C</code> is the non-atomic type corresponding to <code>A</code>.</p>

<p>It is unspecified whether the name of a generic function is a macro or an identifier declared with external linkage. If a macro definition is suppressed in order to access an actual function (e.g. parenthesized like <code>(atomic_init)(...)</code>), or a program defines an external identifier with the name of a generic function, the behavior is undefined.</p>

<h3 id="Parameters">Parameters</h3>

<table class="ref-table ref-params">
<tr><td>obj</td><td>-</td><td>pointer to an atomic object to initialize</td></tr>
<tr><td>desired</td><td>-</td><td>the value to initialize atomic object with</td></tr>
</table>

<h3 id="Return_value">Return value</h3>

<p>(none)</p>

<h3 id="Notes">Notes</h3>

<p><code>atomic_init</code> is the only way to initialize dynamically-allocated atomic objects. For example:</p>

```c
_Atomic int *p = malloc(sizeof(_Atomic int));
atomic_init(p, 42);
```
