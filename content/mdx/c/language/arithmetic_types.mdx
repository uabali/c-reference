<dd><code>1</code>

<code>sizeof(char)</code>

<code>≤</code>

<code>sizeof(short)</code>

<code>long</code>

<p>and pointer are 32-bit)</p>
</li>
</ul>

<dl>
<dd><ul>
<li>
<p>Win16 API</p>
</li>
</ul></dd>
</dl>

<ul>
<li>
<strong>ILP32</strong>

<strong>4/4/4</strong>

<p>(</p>

<h3 id="Real_floating_types">Real floating types</h3>

<p>C has three or six<span class="std std-since std-c23">(since C23)</span> types for representing real floating-point values:</p>

<dl>
<dd><ul>
<li>
<code>float</code>

<p>— single precision floating-point type. Matches</p>

<a href="https://en.wikipedia.org/wiki/Single-precision_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 binary32 format</a>

<p>if supported.</p>
</li>
<li>
<code>double</code>

<p>— double precision floating-point type. Matches</p>

<a href="https://en.wikipedia.org/wiki/Double-precision_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 <code>binary64</code> format</a>

<p>if supported.</p>
</li>
<li>
<code>long double</code>

<p>— extended precision floating-point type. Matches</p>

<a href="https://en.wikipedia.org/wiki/Quadruple-precision_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 <code>binary128</code> format</a>

<p>if supported, otherwise matches</p>

<a href="https://en.wikipedia.org/wiki/Extended_precision" rel="noreferrer" target="_blank">IEEE-754 <code>binary64</code>-extended format</a>

<p>if supported, otherwise matches some non-IEEE-754 extended floating-point format as long as its precision is better than</p>

<code>binary64</code>

<p>and range is at least as good as</p>

<code>binary64</code>

<p>, otherwise matches IEEE-754</p>

<code>binary64</code>

<p>format.</p>

<ul>
<li>
<code>binary128</code>

<p>format is used by some HP-UX, SPARC, MIPS, ARM64, and z/OS implementations.</p>
</li>
<li>
<p>The most well known IEEE-754</p>

<code>binary64</code>

<p>-extended format is 80-bit x87 extended precision format. It is used by many x86 and x86-64 implementations (a notable exception is MSVC, which implements</p>

<code>long double</code>

<p>in the same format as</p>

<code>double</code>

<p>, i.e.</p>

<code>binary64</code>

<p>).</p>
</li>
</ul>
</li>
</ul></dd>
</dl>

<aside class="revision"><p class="rev-mark"><span class="std std-since std-c23">(since C23)</span></p><dl>
<dd><p>If the implementation predefines the macro constant</p>

<code>__STDC_IEC_60559_DFP__</code>

<p>, the following decimal floating-point types are also supported.</p>

<ul>
<li>
<code>_Decimal32</code>

<p>— Represents</p>

<a href="https://en.wikipedia.org/wiki/decimal32_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 decimal32 format</a>

<p>.</p>
</li>
<li>
<code>_Decimal64</code>

<p>— Represents</p>

<a href="https://en.wikipedia.org/wiki/decimal64_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 decimal64 format</a>

<p>.</p>
</li>
<li>
<code>_Decimal128</code>

<p>— Represents</p>

<a href="https://en.wikipedia.org/wiki/decimal128_floating-point_format" rel="noreferrer" target="_blank">IEEE-754 decimal128 format</a>

<p>.</p>
</li>
</ul></dd>
<dd><p>Otherwise, these decimal floating-point types are not supported.</p></dd>
</dl></aside>

<p>Floating-point types may support special values:</p>

<ul>
<li>
<em>infinity</em>

<p>(positive and negative), see</p>

<a href="/reference/c/numeric/math/INFINITY/"><code>INFINITY</code></a>
</li>
<li>
<p>the</p>

<em>negative zero</em>

<p>,</p>

<code>-0.0</code>

<p>. It compares equal to the positive zero, but is meaningful in some arithmetic operations, e.g.</p>

<code>1.0 / 0.0 == INFINITY</code>

<p>, but</p>

<code>1.0 / -0.0 == -INFINITY</code>

<p>)</p>
</li>
<li>
<em>not-a-number</em>

<p>(NaN), which does not compare equal with anything (including itself). Multiple bit patterns represent NaNs, see</p>

<a href="/reference/c/numeric/math/nan.2/">nan</a>

<p>,</p>

<a href="/reference/c/numeric/math/NAN/"><code>NAN</code></a>

<p>. Note that C takes no special notice of signaling NaNs (specified by IEEE-754), and treats all NaNs as quiet.</p>
</li>
</ul>

<p>Real floating-point numbers may be used with <a href="/reference/c/language/operator_arithmetic/">arithmetic operators</a> <code>+</code> <code>-</code> <code>/</code> <code>*</code> and various mathematical functions from <a href="/reference/c/numeric/math/"><code>&lt;math.h&gt;</code></a>. Both built-in operators and library functions may raise floating-point exceptions and set <a href="/reference/c/error/errno/">errno</a> as described in <a href="/reference/c/numeric/math/math_errhandling/"><code>math_errhandling</code></a>.</p>

<p>Floating-point expressions may have greater range and precision than indicated by their types, see <a href="/reference/c/types/limits/FLT_EVAL_METHOD/">FLT_EVAL_METHOD</a>. <a href="/reference/c/language/operator_assignment/">Assignment</a>, <a href="/reference/c/language/return/">return</a>, and <a href="/reference/c/language/cast/">cast</a> force the range and precision to the one associated with the declared type.</p>

<p>Floating-point expressions may also be <em>contracted</em>, that is, calculated as if all intermediate values have infinite range and precision, see <a href="/reference/c/preprocessor/impl/#Standard_pragmas"><code>#pragma STDC FP_CONTRACT</code></a>.</p>

<p>Some operations on floating-point numbers are affected by and modify the state of <a href="/reference/c/numeric/fenv/">the floating-point environment</a> (most notably, the rounding direction).</p>

<p><a href="/reference/c/language/conversion/">Implicit conversions</a> are defined between real floating types and integer, complex, and imaginary types.</p>

<p>See <a href="/reference/c/types/limits/#Limits_of_floating-point_types">Limits of floating-point types</a> and the <a href="/reference/c/numeric/math/"><code>&lt;math.h&gt;</code></a> library for additional details, limits, and properties of the floating-point types.</p>

<aside class="revision"><p class="rev-mark"><span class="std std-since std-c99">(since C99)</span></p><h3 id="Complex_floating_types">Complex floating types</h3>

<p>Complex floating types model the mathematical <a href="https://en.wikipedia.org/wiki/complex_number" rel="noreferrer" target="_blank">complex number</a>, that is the numbers that can be written as a sum of a real number and a real number multiplied by the imaginary unit: a + bi</p>

<p>The three complex types are</p>

<dl>
<dd><ul>
<li>
<code>float _Complex</code>

<p>(also available as</p>

<code>float complex</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
<li>
<code>double _Complex</code>

<p>(also available as</p>

<code>double complex</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
<li>
<code>long double _Complex</code>

<p>(also available as</p>

<code>long double complex</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
</ul></dd>
</dl>

<p>Note: as with all type specifiers, any order is permitted: <code>long double complex</code>, <code>complex long double</code>, and even <code>double complex long</code> name the same type.</p>

```c
#include <complex.h>
#include <stdio.h>
 
int main(void)
{
    double complex z = 1 + 2*I;
    z = 1 / z;
    printf("1/(1.0+2.0i) = %.1f%+.1fi\n", creal(z), cimag(z));
}
```

<p>Output:</p>

```text
1/(1.0+2.0i) = 0.2-0.4i
```

<aside class="revision"><p class="rev-mark"><span class="std std-since std-c11">(since C11)</span></p><p>If the macro constant <code>__STDC_NO_COMPLEX__</code> is defined by the implementation, the complex types (as well as the library header <a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>) are not provided.</p></aside>

<p>Each complex type has the same <a href="/reference/c/language/object/">object representation</a> and <a href="/reference/c/language/object/">alignment requirements</a> as an <a href="/reference/c/language/array/">array</a> of two elements of the corresponding real type (<code>float</code> for <code>float complex</code>, <code>double</code> for <code>double complex</code>, <code>long double</code> for <code>long double complex</code>). The first element of the array holds the real part, and the second element of the array holds the imaginary component.</p>

```c
float a[4] = {1, 2, 3, 4};
float complex z1, z2;
memcpy(&z1, a, sizeof z1); // z1 becomes 1.0 + 2.0i
memcpy(&z2, a+2, sizeof z2); // z2 becomes 3.0 + 4.0i
```

<p>Complex numbers may be used with <a href="/reference/c/language/operator_arithmetic/">arithmetic operators</a> <code>+</code> <code>-</code> <code>*</code> and <code>/</code>, possibly mixed with imaginary and real numbers. There are many mathematical functions defined for complex numbers in <a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>. Both built-in operators and library functions may raise floating-point exceptions and set <a href="/reference/c/error/errno/">errno</a> as described in <a href="/reference/c/numeric/math/math_errhandling/"><code>math_errhandling</code></a>.</p>

<p>Increment and decrement are not defined for complex types.</p>

<p>Relational operators are not defined for complex types (there is no notion of "less than").</p>

<a href="/reference/c/language/conversion/">Implicit conversions</a>

<p>are defined between complex types and other arithmetic types.</p>

<p>In order to support the one-infinity model of complex number arithmetic, C regards any complex value with at least one infinite part as an infinity even if its other part is a NaN, guarantees that all operators and functions honor basic properties of infinities and provides <a href="/reference/c/numeric/complex/cproj/">cproj</a> to map all infinities to the canonical one (see <a href="/reference/c/language/operator_arithmetic/">arithmetic operators</a> for the exact rules).</p>

```c
#include <complex.h>
#include <math.h>
#include <stdio.h>
 
int main(void)
{
    double complex z = (1 + 0*I) * (INFINITY + I*INFINITY);
//  textbook formula would give
//  (1+i0)(∞+i∞) ⇒ (1×∞ – 0×∞) + i(0×∞+1×∞) ⇒ NaN + I*NaN
//  but C gives a complex infinity
    printf("%f%+f*i\n", creal(z), cimag(z));
 
//  textbook formula would give
//  cexp(∞+iNaN) ⇒ exp(∞)×(cis(NaN)) ⇒ NaN + I*NaN
//  but C gives  ±∞+i*nan
    double complex y = cexp(INFINITY + I*NAN);
    printf("%f%+f*i\n", creal(y), cimag(y));
}
```

<p>Possible output:</p>

```text
inf+inf*i 
inf+nan*i
```

<p>C also treats multiple infinities so as to preserve directional information where possible, despite the inherent limitations of the Cartesian representation:</p>

<p>multiplying the imaginary unit by real infinity gives the correctly-signed imaginary infinity: i × ∞ = i∞. Also, i × (∞ – i∞) = ∞ + i∞ indicates the reasonable quadrant.</p>

<h3 id="Imaginary_floating_types">Imaginary floating types</h3>

<p>Imaginary floating types model the mathematical <a href="https://en.wikipedia.org/wiki/imaginary_numbers" rel="noreferrer" target="_blank">imaginary numbers</a>, that is numbers that can be written as a real number multiplied by the imaginary unit: bi The three imaginary types are</p>

<dl>
<dd><ul>
<li>
<code>float _Imaginary</code>

<p>(also available as</p>

<code>float imaginary</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
<li>
<code>double _Imaginary</code>

<p>(also available as</p>

<code>double imaginary</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
<li>
<code>long double _Imaginary</code>

<p>(also available as</p>

<code>long double imaginary</code>

<p>if</p>

<a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>

<p>is included)</p>
</li>
</ul></dd>
</dl>

<p>Note: as with all type specifiers, any order is permitted: <code>long double imaginary</code>, <code>imaginary long double</code>, and even <code>double imaginary long</code> name the same type.</p>

```c
#include <complex.h>
#include <stdio.h>
 
int main(void)
{
    double imaginary z = 3*I;
    z = 1 / z;
    printf("1/(3.0i) = %+.1fi\n", cimag(z));
}
```

<p>Output:</p>

```text
1/(3.0i) = -0.3i
```

<aside class="revision"><p class="rev-mark"><span class="std std-until std-c11">(until C11)</span></p><p>An implementation that defines <code>__STDC_IEC_559_COMPLEX__</code> is recommended, but not required to support imaginary numbers. POSIX recommends checking if the macro <a href="/reference/c/numeric/complex/Imaginary_I/">_Imaginary_I</a> is defined to identify imaginary number support.</p></aside>

<aside class="revision"><p class="rev-mark"><span class="std std-since std-c11">(since C11)</span></p><p>Imaginary numbers are supported if <code>__STDC_IEC_559_COMPLEX__</code><span class="std std-until std-c23">(until C23)</span><code>__STDC_IEC_60559_COMPLEX__</code><span class="std std-since std-c23">(since C23)</span> is defined.</p></aside>

<p>Each of the three imaginary types has the same <a href="/reference/c/language/object/">object representation</a> and <a href="/reference/c/language/object/">alignment requirement</a> as its <em>corresponding real type</em> (<code>float</code> for <code>float imaginary</code>, <code>double</code> for <code>double imaginary</code>, <code>long double</code> for <code>long double imaginary</code>).</p>

<p>Note: despite that, imaginary types are distinct and <a href="/reference/c/language/compatible_type/#Compatible_types">not compatible</a> with their corresponding real types, which prohibits aliasing.</p>

<p>Imaginary numbers may be used with <a href="/reference/c/language/operator_arithmetic/">arithmetic operators</a> <code>+</code> <code>-</code> <code>*</code> and <code>/</code>, possibly mixed with complex and real numbers. There are many mathematical functions defined for imaginary numbers in <a href="/reference/c/numeric/complex/"><code>&lt;complex.h&gt;</code></a>. Both built-in operators and library functions may raise floating-point exceptions and set <a href="/reference/c/error/errno/">errno</a> as described in <a href="/reference/c/numeric/math/math_errhandling/"><code>math_errhandling</code></a>.</p>

<p>Increment and decrement are not defined for imaginary types.</p>

<tr><td></td><td>This section is incomplete Reason: review other ops, link library</td></tr>
</table>

<a href="/reference/c/language/conversion/">Implicit conversions</a>

<p>are defined between imaginary types and other arithmetic types.</p>

<p>The imaginary numbers make it possible to express all complex numbers using the natural notation <code>x + I*y</code> (where I is defined as <a href="/reference/c/numeric/complex/Imaginary_I/">_Imaginary_I</a>). Without imaginary types, certain special complex values cannot be created naturally. For example, if I is defined as <a href="/reference/c/numeric/complex/Complex_I/">_Complex_I</a>, then writing <code>0.0 + I*INFINITY</code> gives NaN as the real part, and <code>CMPLX(0.0, INFINITY)</code> must be used instead. Same goes for the numbers with the negative zero imaginary component, which are meaningful when working with the library functions with branch cuts, such as <a href="/reference/c/numeric/complex/csqrt/">csqrt</a>: <code>1.0 - 0.0*I</code> results in the positive zero imaginary component if I is defined as <a href="/reference/c/numeric/complex/Complex_I/">_Complex_I</a> and the negative zero imaginary part requires the use of <a href="/reference/c/numeric/complex/CMPLX/">CMPLX</a> or <a href="/reference/c/numeric/complex/conj/">conj</a>.</p>

<p>Imaginary types also simplify implementations; multiplication of an imaginary by a complex can be implemented straightforwardly with two multiplications if the imaginary types are supported, instead of four multiplications and two additions.</p></aside>

<h3 id="Range_of_values">Range of values</h3>

<p>The following table provides a reference for the limits of common numeric representations.</p>

<p>Prior to C23, the C Standard allowed any signed integer representation, and the minimum guaranteed range of N-bit signed integers was from \(\scriptsize -(2^{N-1}-1)\)-(2N-1 -1) to \(\scriptsize +2^{N-1}-1\)+2N-1 -1 (e.g. <strong>-127</strong> to <strong>127</strong> for a signed 8-bit type), which corresponds to the limits of <a href="https://en.wikipedia.org/wiki/one%27s_complement" rel="noreferrer" target="_blank">one's complement</a> or <a href="https://en.wikipedia.org/wiki/Signed_number_representations#Sign-and-magnitude_method" rel="noreferrer" target="_blank">sign-and-magnitude</a>.</p>

<p>However, all popular data models (including all of ILP32, LP32, LP64, LLP64) and almost all C compilers use <a href="https://en.wikipedia.org/wiki/two%27s_complement" rel="noreferrer" target="_blank">two's complement</a> representation (the only known exceptions are some compilers for UNISYS), and as of C23, it is the only representation allowed by the standard, with the guaranteed range from \(\scriptsize -2^{N-1}\)-2N-1  to \(\scriptsize +2^{N-1}-1\)+2N-1 -1 (e.g. <strong>-128</strong> to <strong>127</strong> for a signed 8-bit type).</p>
